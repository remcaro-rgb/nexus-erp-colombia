# Shared Constitution (binding on every agent)

Version 1.1.0. Research date 2026-11-08. Owner: P00 (orchestrator). **Read-only for all workers.**

## C1. Product invariants (never violate)
1. **Money ⇒ ledger, in-line.** Every *posting trigger* in shared/07 (issued invoice, credit/debit note, validated support document,
   received goods, delivered goods, POS sale close, payment/receipt, payroll approval/payment, depreciation run, revaluation, FX revaluation, write-off,
   inventory adjustment) creates its journal entry **in the same database transaction** as the business document state change.
   If posting fails, the business transaction rolls back. No batch "post later", except the explicitly scheduled period processes
   (depreciation run, FX revaluation, accruals), and those also post atomically per run.
2. **Stock ⇒ inventory, in-line.** Every stock movement (receipt, delivery, POS sale, return, transfer, adjustment, production issue/receipt `[A]`)
   updates the stock ledger, on-hand/reserved quantities, and valuation layers in the same transaction, and also the GL when valuation is perpetual.
3. **Non-posting documents never touch the GL:** quotations, sales orders, purchase requests/orders, reservations, CRM opportunities, drafts, simulations.
   Commitments/encumbrances may be tracked only in sub-ledgers marked `non_gl`.
4. **Double entry:** every journal entry balances to zero per currency in transaction currency AND in company functional currency (COP), within
   0 tolerance after rounding lines are generated by the posting engine (never by callers).
5. **Immutability:** posted journal entries, stock moves, and fiscal documents are append-only. Corrections are made only by reversal or adjusting documents
   (credit/debit notes, notas de ajuste, reversal entries) that link to the original. Period locks and fiscal-year close prevent back-posting except through an audited reopen with SoD.
6. **Tenant ≠ company.** Tenant = subscribing customer account (security + billing boundary). Company = legal entity (NIT) inside a tenant.
   A tenant may have many companies. Every business row carries `tenant_id` and (where applicable) `company_id`. Intercompany
   transactions happen only between companies of the same tenant.
7. **Every business process is reachable by API.** The UI, AI agent, MCP server, importer, and scheduler call the same application service layer and
   authorization path. No feature is UI-only, and no tool gets a private write path.
8. **Authorization is deny-by-default** and enforced on one path (`iam.policy`) covering ORM querysets, API serializers, exports, reports,
   search, AI tools, MCP tools, logs, and caches. PostgreSQL RLS is a second, independent line of defense for tenant/company isolation.
9. **Regulatory values are data, not code.** Rates, thresholds, UVT, minimum wage, transport allowance, surcharges, calendars, and DIAN code lists live in
   `tax.parameters` (owned by P06; payroll and every other module read through `kernel.parameters`) with `valid_from`, `valid_to`, `source_id` (from shared/05), and `status`
   (`VERIFIED-PRIMARY` | `VERIFIED-SEARCH` | `VERIFIED-SECONDARY` | `UNKNOWN` | `DISPUTED`, defined in shared/04). In production, a value that is UNKNOWN or lacks a legal-review stamp blocks the calculation (EG-7). DISPUTED values (official but under litigation) compute only with a legal-review stamp, and a warning plus a parameter snapshot is stored. Calculations dated where a needed parameter is UNKNOWN **fail with a clear error**.
   They never guess. DISPUTED values compute but raise a compliance warning.
10. **External fiscal reality is not rolled back.** A DIAN-validated document (CUFE/CUDE/CUNE) can only be corrected by notes/adjustments.
    Outbound integrations are at-least-once with idempotency keys. Nobody claims exactly-once delivery to external systems.
11. **Fail closed in production** for anything that depends on an unmet external gate (shared/09). For example, if DIAN credentials are missing, the
    production tenant cannot "issue" electronic invoices. It can only save them as drafts, and the reason is shown.
12. **No disconnected finalization.** A sale, return, payment, cash movement, stock movement, fiscal number, or fiscal document is *final* only when the server
    transaction that posts its GL and stock entries commits (C1-1, C1-2). Clients (POS PWA, mobile, AI, MCP, importer) never finalize any of these while
    disconnected from the application server. No queued "post later at sync", no locally assigned final fiscal numbers, no local CUDE/CUFE, no printed fiscal receipts
    and no payment capture without a committed server transaction. Offline clients may only browse cached data and keep clearly labelled **unposted drafts**.
    The only exception is the `[A]` flag `pos_offline_fiscal_selling` (ADR-015): disabled by default, never used to satisfy any `[P]` test or gate, and
    enabled only after EG-13. A DIAN/PT outage while our server is reachable is **not** an exception: the sale still commits in-line, and only the fiscal
    transmission follows the contingency flow (R-FE-05, P15).

## C2. Engineering rules
1. Language/tooling: Python 3.13, Django 5.2 LTS, DRF, PostgreSQL 18, Celery+Redis/Valkey, React 18+/TypeScript strict, Vite. Pin exact versions in lock files.
   Before pinning, verify each dependency's current support window. Record the evidence in `docs/dependency-evidence.md` (owner P03).
2. Money: Python `decimal.Decimal` only. DB `NUMERIC`. No floats anywhere in money, quantity, rate, or percentage paths. This is enforced by lint (P03) and tests.
   Precision: amounts `NUMERIC(20,4)` stored, rounded to the currency minor unit at the document-total level per the rounding policy in shared/07.
   Quantities `NUMERIC(20,6)`, unit costs `NUMERIC(24,8)`, FX rates `NUMERIC(24,10)`, percentages `NUMERIC(9,6)`.
3. IDs: UUIDv7 primary keys (`kernel.ids.new_id()`). Human document numbers come from `kernel.sequences` (gap policy per document type; fiscal
   sequences must use DIAN-authorized ranges and never reuse a number).
4. Time: store UTC `timestamptz`. Every company has `timezone` (default `America/Bogota`), and business dates (`posting_date`, `document_date`) are `date` values
   in company local time. Scheduler cron expressions are evaluated in the schedule owner's company timezone.
5. Locale: default UI `es-CO`. English is a second locale. Number format `1.234.567,89`. Currency default COP. Multicurrency allowed per document.
6. Transactions: application services use `kernel.uow.unit_of_work()` (atomic plus outbox plus audit). Row locks: `SELECT ... FOR UPDATE` on
   stock balance rows and sequence rows, in a fixed lock ordering (by `(item_id, warehouse_id, lot_id)` ascending) to avoid deadlocks. Every
   mutating endpoint accepts `Idempotency-Key`, and replays return the original response.
7. Events: domain events are written to `kernel_outbox` in the same transaction. The relay publishes to Celery. Consumers are idempotent
   (dedupe table keyed by `event_id`). Event schemas are versioned in `contracts/events/`.
8. Tests: pytest + pytest-django + hypothesis (property tests for money/stock), Playwright for E2E, schemathesis or an equivalent tool for OpenAPI contract tests.
   **Forbidden in release:** skipped tests without a linked blocker ID, `assert True`, mocks of the code under test, endpoints that return fixed data,
   `TODO` in a shipped code path, and catch-all `except: pass`. CI fails if any of these appear (P03 implements the check).
9. Each agent writes tests only under its own module test paths (shared/02) and never edits another module's tests.
10. Security: OWASP ASVS 5.0 L2 baseline (L3 for auth, payments, payroll), OWASP API Top 10 2023, OWASP Top 10 for LLM Applications 2025.
    Secrets come only from the secret provider (ADR-012). Never log secrets, tokens, full card data, or sensitive personal data (shared/04 §DP).
11. Accessibility: WCAG 2.2 AA for all UI. Keyboard-complete dense tables. Visible focus. No information conveyed by color alone.

## C3. Collaboration rules
1. Work only inside your owned paths (shared/02). Read anything. To change a shared contract, open a CCR file
   `contracts/change-requests/CCR-<agent>-<n>.md` and stop work that depends on it until P00/P02 approves.
2. Never edit: `shared/`, `contracts/` (except your own module fragment after G0, per shared/02), root manifests (`pyproject.toml`,
   `package.json`, `docker-compose*.yml`, `erp/settings/*`, `erp/urls.py`), unless you own them. Ask the owner with a CCR, using the "dependency request" template, to add a dependency.
3. Migrations: only for your own Django apps, and only after rebasing on the latest `main`. The merge queue serializes merges. `makemigrations --check`
   must be clean. No migration may edit another app's tables. Cross-app data needs go through that app's service API.
4. Handoff report at the end, in `docs/handoffs/<prompt-id>.md`: what was built, the endpoint list, events emitted/consumed, the permission codes,
   tests with counts, known gaps mapped to blocker IDs, and evidence (test output summaries). Never claim more than the tests prove.
5. If something is ambiguous, choose the safer option (fail closed, no posting, require approval), record the assumption in your handoff, and continue.
   Stop only for a hard blocker. Do not ask the user for things the shared docs already decide.
