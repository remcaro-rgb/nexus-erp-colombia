## What was built

* **HR models** (`backend/hr/models.py`, migrations `0001_initial`, `0002_security` = RLS ENABLE+FORCE on every table,
  composite company FK, append-only `hr_contract_history` trigger): `OrgUnit`, `Position`, `Employee` (Ley 1581
  classification, `data_consent_at`, `biometric_consent_at`, bank account encrypted at rest — `hr/crypto.py`),
  `EmploymentContract` (types INDEFINIDO/FIJO/OBRA_LABOR/APRENDIZAJE/PRESTACION_SERVICIOS — the last is not payroll),
  `ContractHistory`, `DataUpdateRequest`.
* **HR API** (`/api/v1/hr/*`, generic secured CRUD in `hr/api/crud.py` on the IAM `SecuredView`): employees
  (+`:bulk` all-or-nothing), contracts (+`:amend`, `:terminate`), positions, org-units; deny-by-default, company row
  scope, field masks (salary/bank = confidential, health/pension = sensitive-pii), `Idempotency-Key` on every write,
  `If-Match` on PATCH, foreign ids 404. Contract rules: one payroll contract in force per employee (`contract_overlap`),
  integral salary ≥ `hr.salario_integral.min_smmlv` × `smmlv` (parameters; UNKNOWN fails closed), amendments/terminations
  append history and emit `hr.contract.changed.v1`; contracts are never deleted.
* **HR interface for payroll** (`hr/interfaces.py`, `hr/directory.py`): `PayrollEmployeeSource` in exactly P13b's frozen
  shape; `DbPayrollEmployeeSource` returns payroll contracts overlapping the period with the APPROVED timesheet hours;
  registered at app ready against HR's Protocol and — when the payroll app is installed — against
  `payroll.interfaces.PayrollEmployeeSource` with payroll's own dataclass (`hr/wiring.py`).
* **Time keeping** (`backend/timekeeping/**`): shifts, clock events (`:clock-in`/`:clock-out` alternate; BIOMETRIC only
  with explicit consent and only the device-side match result stored; WEB/KIOSK_PIN/KIOSK_QR/MOBILE always available),
  absences incl. vacations, overtime requests, timesheets (DRAFT → SUBMITTED → APPROVED | REJECTED; SoD: the
  submitter/requester never decides; reject needs a reason). **Classification engine** (`classification.py`, pure):
  splits intervals at midnight, at the night window of the date of work and at the end of the ordinary hours into
  `{rest_}{ordinary|overtime}_{day|night}`; parameters per date (`hr.jornada.*`), daily overtime limit warning.
  Timesheet submit classifies the month's marks and stores hours + parameter snapshots; approval emits
  `timekeeping.timesheet.approved.v1`.
* **Employee portal** (`backend/hr/portal/**`, `/api/portal/v1/employee/*`, all on `iam.external.portal.PortalView`
  with `portal_kind = "employee"`): payslips (+pdf), certificates (+pdf: LABORAL, INGRESOS_RETENCIONES), vacations
  (GET/POST), data-updates (GET/POST), profile, and the dashboard KPIs (`/employee/kpis`, CCR P13a-2).
  * Scope only from the token's account (employee + company); querysets through `PolicyEngine.scope_queryset`
    (company + `employee_id`), payslips from `EmployeePayslipSource` called with the token's employee **and** an
    ownership check per document; foreign ids → 404 `portal_document_not_owned`; scope ids in query/body →
    403 `external_account_scope_violation`; field allowlists only; every document access audited.
  * Certificates have deterministic UUIDv5 ids per employee (no table; a foreign id can never match). PDFs go
    through `kernel.interfaces.DocumentRenderer` (D-005) with the watermark
    `SINTÉTICO — NO LEGALMENTE VERIFICADO (formato de desarrollo, no certificado) · Parámetros: smmlv=VERIFIED-PRIMARY
    (FIXTURE — NOT LEGALLY VERIFIED) · …` (UNKNOWN parameters are shown as UNKNOWN, never invented).
  * Vacations: a portal request is a timekeeping `Absence` (`VACACIONES`) created SUBMITTED; the manager approves
    with `POST /api/v1/timekeeping/absences/{id}:approve` (balance re-checked under the employee row lock).
    `request_status` = SUBMITTED | APPROVED | REJECTED | TAKEN (APPROVED and last day in the past).
  * Balance (`hr/vacations.py`): accrued = 30/360 service days × `hr.vacaciones.dias_habiles_anio` / 360;
    KPI = accrued − taken − approved pending; a new request must also fit the SUBMITTED ones
    (`vacation_balance_insufficient`); days = business days without Colombian holidays.
  * Data updates: only `email`, `phone`, `address` (others → `field_forbidden`); HR approves/rejects with
    `/api/v1/hr/data-updates/{id}:approve|:reject` (CCR P13a-2) and the change is applied to the employee.
* **UI** (`frontend/src/features/hr/portal/**`): `portal.descriptor.ts` contributes Desprendibles, Certificados,
  Vacaciones, Actualización de datos and Perfil to the P08 portal shell (Inicio stays the shell dashboard);
  fixture label on certificates; decimal-string money formatting; typed API client.

## Decisions taken under ambiguity

* **Contract status**: no approval action exists for contracts in the frozen API, so a created contract is
  `APPROVED` (= in force); `:terminate` → `CANCELLED` with `termination_date`; DELETE is refused (409).
* **Vacation requests are absences** (`VACACIONES`), so the documented `timekeeping/absences/{id}:approve` is the
  manager approval; no separate vacation table. TAKEN is derived (approved, last day before today).
* **Accrual convention** 30/360 from the first contract start, capped by the latest contract's end/termination;
  rounding down to 2 decimals. Entitlement is a parameter (no hard-coded 15).
* **Payslips come from payroll**: HR never computes pay; the portal reads POSTED payslips through
  `EmployeePayslipSource` (adapter over P13b's tables when installed; otherwise 503 `service_unavailable`, KPI
  `not_available`).
* **Certificates are derived** (no stored rows): the income certificate totals the employee's own POSTED payslips of
  the year; the official formato 220 is EXTERNAL and not claimed.
* **`kernel.parameters.enforce` overwrites the error code** with the parameter code; `hr.services.parameter` restores
  the stable codes `parameter_unknown` / `parameter_not_verified` (parameter named in `errors`).
* **Contract `total`** is `null` (a contract has no document total; echoing the salary there would leak a
  confidential value under an `internal` classification).
* **Numbers** `CT-/AUS-/HE-/TS-<year>-<n>` are internal references (no DIAN numbering, no `kernel.sequences` range).

## Known limits

* `/api/v1/hr/self-service/*` (internal self-service) is not routed (CCR P13a-2); employees use the portal.
* PDF links in the UI are plain `href`s: in DEV they need the portal session cookie/BFF of P08 (bearer-only clients
  must fetch the PDF with the API client).
* Weekly maximum hours, Sunday habituality and compensatory rest are not yet evaluated by the classification engine
  (hours buckets only; surcharge rates are payroll formulas). Shift rotations/planning beyond shift templates,
  onboarding/offboarding checklists, employee documents and geofence configuration are not in this part.
* DEV stack: HR parameters are missing from the P06 seed (CCR P13a-3) — the vacation KPI shows `not_available`
  until they are added.
