* `:transfer` `parameters`: `dimensions{…}`, `location`, `custodian_employee_id`, `branch_id`, `effective_date`.
* `:dispose`: `reason` (required), `effective_date`, `parameters` {`kind` SALE|SCRAP|DONATION, `proceeds`, `vat`,

* Depreciation runs: `lines[]` only for UNITS assets (`item_id` = asset id, `quantity.value` = units of the period).
* Physical counts: `lines[].description` = scanned tag; `:submit` rewrites the lines (found, unknown without `item_id`,
  missing with quantity 0); `:approve` must be done by another person (`sod_violation`).

## Decisions taken under ambiguity
1. **Per-book posting** through the ledger planner restricted to one book (CCR P14-1) — the only way to post separate
   NIIF/fiscal entries with the frozen interface while keeping all ledger validations.
2. Contract `FixedAsset.status` ∈ {ACTIVE, ARCHIVED}: DISPOSED → ARCHIVED, every other lifecycle → ACTIVE; the lifecycle is
   in the register report rows (CCR P14-7).
3. Components = assets with `parent`; disposing a parent with active components is refused (`components_active`).
4. Sale proceeds go to the clearing role `ASSET_DISPOSAL_PROCEEDS`; AR and VAT belong to the P10 invoice (CCR P14-4), so
   AR (a control account) is never posted from assets.
5. Revaluation uses the elimination method; revaluation and impairment apply to NIIF books only (fiscal cost basis
   unchanged). On derecognition the surplus goes to `RETAINED_EARNINGS`.
6. A run charges one period per eligible asset (no automatic catch-up of skipped months; the KPI `sin_depreciar` shows
   assets without a run). Runs use the shell period (monthly periods 1–12).
7. `:post` of an already posted run returns it unchanged (idempotent per company+book+period); a second run for the same
   book and period is `depreciation_run_exists`. Run reversal is not in the contract (corrections: estimate change /
   next period).
8. SoD: enforced on physical-count approval (submitter ≠ approver). Depreciation/revaluation posting rely on the
   permission split (`*.create` vs `*.post`); no extra maker-checker rule.
9. Change of estimate is a service function (`assets.service.change_estimate`), audited, not routed (no contract path).
10. QR labels are rendered client-side (no PDF/QR dependency in the lockfiles; P17 owns server-side rendering later).
