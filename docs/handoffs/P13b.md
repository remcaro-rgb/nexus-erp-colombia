## What was built

* **Models** (`backend/payroll/models.py`, migrations `0001_initial`, `0002_security`): `PayrollPeriod`,
  `PayrollConcept` (+`formula_id`, `depends_on`, `account_role`, `salary_base`, `electronic_payroll_code`,
  `rounding_places`, `is_user_defined`), `PayrollNovelty`, `PayrollRun` (DRAFT → CALCULATED → APPROVED → POSTED →
  PAID, stores the parameter snapshot and the graph order), `Payslip`, `PayslipLine` (formula id/version/hash, inputs,
  explain trace, parameter snapshots), `ElectronicPayrollDocument`. RLS (ENABLE+FORCE, tenant + bound companies) on
  every table; payslips and lines are immutable once posted (DB trigger `kernel_forbid_mutation`).
* **Concept graph** (`backend/payroll/concepts/graph.py`): every concept is one node of the P07 `FormulaGraph`
  with the concept code as formula code, so formulas read earlier results by code. DAG check, deterministic
  topological order (Kahn, ties by code), D-008 budgets and the explain trace all come from the shared engine — no
  Python evaluation anywhere (static scan in T-PAY-FORMULA-04).
* **Legal parameters as inputs** (`backend/payroll/concepts/parameters.py`): a formula declares `param_<name>`
  inputs from a versioned catalogue (`CATALOGUE_VERSION = 2026.1`, e.g. `param_smmlv → smmlv`,
  `param_salud_empleado → ss.salud.empleado`); values come only from `kernel.parameters.ParameterProvider` (P06 store)
  for the period end date. Unknown names, missing or UNKNOWN values → `payroll_parameter_unknown` (fail closed, before
  any employee is evaluated); production rules → `parameter_not_verified`. Every value read is snapshotted on the run,
  the payslip and the line, labelled `NOT LEGALLY VERIFIED` unless it has a legal-review stamp and is not synthetic.
* **Inputs a payroll formula may declare** (anything else is rejected on save): `salary`, `days_worked`,
  `period_days`, `integral_salary`, `exonerated`, `arl_risk_class`, `contract_type`, `novelty_amount`,
  `novelty_quantity`, `period_start`, `period_end`, `hours_<type>`, `param_<name>`.
* **Runs** (`backend/payroll/runs.py`): calculate (only DRAFT/CALCULATED, else `payroll_run_locked`), approve (SoD:
  approver ≠ calculator), post (one UoW: payslips immutable + balanced journal via `PostingService`, journal
  `PAYROLL`, + `payroll.run.posted.v1`), pay (POSTED → PAID; the bank file/payment entry is P16's), simulate (exact
  calculation and journal preview, nothing persisted).
* **Payslips / nómina electrónica** (`backend/payroll/payslips.py`): payslip JSON with the explain per line and the
  legal label; amounts and the employee are masked (`null` + `masked[]`) unless the field policy
  (`field_mask(ctx, "payroll.payslip")`) grants them. Electronic payroll: one document per period with a
  NominaIndividual entry per employee from POSTED payslips and the concepts' DIAN element mapping; `:adjust` creates
  a NominaIndividualDeAjuste (Reemplazar/Eliminar) and supersedes the original. Transmission, CUNE and signature are
  EXTERNAL (P15 FiscalGateway): status `SIMULATED_NOT_TRANSMITTED`, label `SIMULADO — FIXTURE_NOT_CERTIFIED`.
* **API** (`backend/payroll/urls.py`, auto-mounted at `/api/v1/payroll/`): periods (list/create/get), concepts
  (CRUD + `:validate-graph`), novelties (list/create/get/`:bulk`), runs (list/create/get + `:calculate`, `:approve`,
  `:post`, `:simulate`, `:pay`), payslips (list/get), electronic-payroll (list/create/get + `:generate`, `:adjust`).
  Only documented operations; `Idempotency-Key` on every write; `If-Match` on concept PATCH/DELETE.
* **UI** (`frontend/src/features/payroll`): `ConceptsPage` (evaluation-order view, server graph validation, legal
  parameters with labels), `PayslipExplain` (lines, formula version, trace, parameter statuses, NOT LEGALLY VERIFIED
  badge, masked amounts as •••), typed API client, tab contribution `talento › nomina › conceptos`.

## How to use it

1. Author a formula in the workflow formulas API with `domain: "payroll"`, **code = the concept code**, inputs from
   the list above, at least one test case; submit; a second person approves (P07 lifecycle, SoD).
2. `POST /api/v1/payroll/concepts` with `formula_id` (and `depends_on`, defaulting to the formula's). Saving parses
   and type-checks the expression in the payroll schema and checks the company graph: a cycle is
   `formula_dependency_cycle`, an unknown dependency `formula_unknown_identifier`, an unknown `param_*`
   `payroll_parameter_unknown`.
3. Period → novelties → run → `:calculate` → `:approve` (another person) → `:post`.

## Decisions taken under ambiguity

* **Formula ownership.** The frozen contract gives the concept a `formula_id`, so the formula lives in P07's
  `workflow.Formula` (domain payroll) with P07's lifecycle (DRAFT → PENDING_APPROVAL → ACTIVE, author ≠ approver).
  The concept has no own approval action (none in the contract); a concept may reference a DRAFT formula, but the
  calculation needs the ACTIVE version effective on the period end date (`formula_not_approved`).
* **Formula code = concept code** (convention, documented): P07 validates a formula against the ACTIVE formulas of
  its domain, so dependent formulas name their dependencies by those codes; the payroll graph mirrors it. Manual
  concepts (no formula) evaluate `novelty_amount`; a concept that other formulas reference should itself be a
  formula (`novelty_amount` works as one), because P07 cannot see manual concepts.
* **Percent parameters** are handed to formulas in percent units (4 for 4 %; the provider returns 0.04), matching
  how the store is written and the DSL's `percent(x, p)`; the snapshot keeps the provider value.
* **Calculation date** of legal parameters = period end date. **Days**: 30-day commercial month (MONTHLY 30,
  BIWEEKLY 15, WEEKLY 7) unless the HR source provides `days_worked`.
* **Rounding**: line amounts ROUND_HALF_UP to 2 places (D-001); formulas may round themselves earlier.
* **Posting roles** (CCR P13b-3): DEVENGO Dr expense · DEDUCCION Cr deduction liability · net pay Cr
  `PAYROLL_NET_PAYABLE` (party = employee) · APORTE/PROVISION Dr expense, Cr contributions/provisions liability;
  aggregated by role, side and cost center.
* **Run number** `NOM-<period>-<n>` (no DIAN numbering involved, no `kernel.sequences` range required).
* **Novelties after posting** are refused (`payroll_run_locked`): corrections go to the next period.

## Known limits / not delivered in this part

* Legal concept formulas (IBC, FSP scale, withholding procedures, prestaciones, vacations), liquidations, PILA files,
  payslip PDF, reports and the KPI provider are not implemented here; the concept/formula engine they need is.
  The corresponding documented routes (`liquidations`, `pila-files`, `payslips/{id}/pdf`, `reports/*`) are not routed.
* Real `LedgerPostingService` needs the payroll account roles (CCR P13b-3); tests use the PostingService double.
* HR interface: consumer-side Protocol + fake until P13a registers the provider (CCR P13b-1).
* The concepts page does not embed the formula editor; formulas are authored with the shared P08 editor through
  the workflow formulas screen/API.
* Legal golden cases remain the external blocker EG-7 (legal review); every fixture value is NOT LEGALLY VERIFIED.
