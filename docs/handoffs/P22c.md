## What was built
### Feature e2e runner (real UI on the real API)
* `tests/cross_module/qa_harness/e2e.py`: per test id, builds a synthetic world on the real PostgreSQL test DB with the
  module kits' real services (P04 policy + LocalIssuer tokens, P05, P09, P10, P11, P13, P16; `transactional_db`), serves
  the real Django app on `127.0.0.1:<ephemeral>` (threaded wsgiref, connections closed per request), runs Playwright
  (system Chrome) on `tests/e2e/features/playwright.config.ts --grep <ID>` and judges the JSON report.
* `tests/e2e/features/support/stack.ts` starts the P08 Vite dev server (`frontend/vite.config.ts`, `/api` proxied to
  the live origin) and swaps `frontend/index.html`'s entry for `support/app-main.tsx`, which mounts the real `App` with a
  synthetic signed-in session (`setAuth`, P08's test injection point). `augment: true` adds pages delivered by their
  owners but not registered in the shell descriptor (only keys the owner did not register).
* Gaps: a step with no UI (or a UI step broken by a product bug) is done through the public API with
  `app.gap(DEF, what, fn)` so the later steps still run; the gap fails the spec. The runner reports **strict XFAIL**
  only if the failures are exactly the registered gaps; any other failure is FAILED; a registered gap that is no
  longer hit fails (strict). XFAIL is "skipped" in JUnit, so `featctl` never counts it as PASSED.
* Keyboard (`tabTo`) and accessible-name (`expectLabelledControls`) checks on each screen; uncaught page errors fail.

### Leak/IDOR suite T-X-QA-03 (`tests/security/test_sec_idor_features.py`, `idor_world.py`)
Real data: tenant T1 = G2 gate world with real documents (items, stock, RFQs + quotes for two suppliers, B-only RFQ,
sent POs, receipt, RC, sales order/delivery, formula), tenant T2; portal identities supplier A/B, customer, employee
onboarded through the real P04 invitation flow. Scope = every implemented contract operation under the
FEATURES-ADDENDUM API prefixes (363 internal ops) and every `/api/portal/v1` op (56).
* Internal: anonymous, no-grant (BFLA), BETA-only user on ALFA (cross-company), BETA-only in its company with ALFA ids,
  T2 admin with T1 ids (cross-tenant BOLA), portal token on internal routes; lists/searches (`?q=`) scanned for foreign
  ids. Object ids come from the T1 admin's own lists and are fetched by the admin first (positive control). 2,206 cases.
* Portal: anonymous/internal/T2 tokens refused; cross-kind refused; supplier A with B-only ids and internal ids → 404;
  lists/search/`party_id` injection show no B data or internal notes; A reaches its own objects (positive control).
* Mutation self-test: with the P04 decision forced to "granted" the suite reports ≥ 50 BFLA findings.
* Four non-leaking status deviations are registered (DEF-P22-070…073) with their own strict-xfail tests; a registered
  row that also leaked data would still fail the main test. Matrices: `reports/leak/p22c-idor-*-{matrix.csv,summary.json}`.

### Wiring defects (`tests/cross_module/test_xm_e2e_wiring.py`)
Strict xfail per delivered-but-unregistered page (DEF-P22-012…015) + a self-test of the checker.

## Decisions taken under ambiguity
1. "Needs the running dev stack": the dev stack (`make dev-up`) was started and left running, but it has no tenant with
   write roles until P21's seed (`make dev-seed` → "SKIPPED — seed_demo not present", wave 8) and its Keycloak cannot
   mint tokens for kit users. The specs therefore run the real SPA against an in-process real Django + PostgreSQL world
   (same precedent as T-ACC-DIM-08, accepted at G1, but with the real API instead of a fake). Re-pointing them at the
   compose stack is a matter of the world builder once P21 seeds users.
2. Missing UI step ⇒ gap + strict XFAIL, not a silent API substitute and not a skip; product bug on an existing step
   (044, 065) ⇒ hard FAILED.
3. T-X-QA-03: non-leaking status deviations (empty 200 list, 422 before 403) are registered with strict xfail; any data
   in a body, 2xx on a foreign object or a write, or a 5xx fails the main test.
4. CCR P11b-1 (P11b migrations join the `purchasing` app only once imported): `pytest_collection_finish` in the P22
   conftests imports `purchasing.requisitions`/`portal` before the test DB is built. Without it a fresh test DB lacks the
   P11b tables whenever no collected module imports them (seen with the IDOR suite).
5. AI agent / MCP leak cases: P19 (AI) and P20 (MCP server) are later waves; no AI tool or MCP surface is implemented
   (`/mcp/` route absent from the URLconf). The P22a principals already model them; cases will be added when they land.
