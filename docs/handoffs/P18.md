## What was built
* **Engine** (`backend/dataio/service.py`): upload → auto-map (header names + Spanish/English synonyms, saved mapping
  profiles) → validate/dry-run → commit in batches → report; cancel; resume.
  * The dry-run executes the **real owner-service calls** in a transaction that is always rolled back. Each row runs
    in a savepoint, so every row error is collected.
  * A job with any row error is `FAILED` and applies **zero rows** (`import_validation_failed`, row-level errors:
    row / column / code / message).
  * Commit runs in batches (`batch_size`; 0 = one all-or-nothing batch). Each batch is one unit of work that inserts
    `ImportBatch(job, batch_no)` (unique) and advances `batches_done`. A crash between batches resumes without
    duplicates (tested with failure injection).
  * Upsert by natural key, with modes `create_only | update_only | upsert`. An unchanged row is never rewritten:
    version stays the same and no audit is written.
  * Hierarchies (dimensions, locations) use two-pass resolution: a topological order inside the file, so children
    may come before parents. Cycles and their descendants become row errors (`hierarchy_cycle`).
* **Idempotent by batch hash**: sha256 over entity, mode and the canonical typed rows. A batch that would change data
  and was already committed (`effective=True`) is refused with `import_duplicate_batch`. The DB backstop is a partial
  unique index.
* **Formats** (`backend/dataio/formats.py`):
  * Parsing: CSV (UTF-8/BOM, `;`/`,` auto-detected, optional es-CO decimal comma), XLSX (multi-sheet), JSON Lines, and
    ZIP packages (members named `<entity>.*`).
  * Limits: file size, row count, member count, uncompressed size and compression ratio.
  * Rejected: zip-slip, nested archives, and XML with a DTD or entities (bomb/XXE).
  * Exports neutralise formulas (`'` before `= + - @ TAB CR`) in CSV and XLSX; import undoes the app's own prefix.
  * The XLSX core properties carry a user/time watermark.

## Decisions taken under ambiguity
1. **The duplicate batch rule only refuses batches that would change data.**
   * Why: the batch hash is computed over canonical typed rows, so the CSV, XLSX and JSONL exports of the same data
     are the same batch. Refusing them would break "export → import is a no-op".
   * Effect: an all-unchanged re-import commits as a no-op with `effective=False`. A replay that would rewrite rows
     changed since then gets `import_duplicate_batch`.
2. **Validation errors make the job terminal `FAILED`** (KPI "lotes rechazados"). The user loads the corrected file
   into a new import, and every rejected batch stays countable.
3. **Commit runs synchronously** and answers 202 with a finished `Operation`; the job state machine gives
   idempotency. Inside the request transaction (ModuleSecuredView), batches are savepoints, and the HTTP handler
   *returns* problem responses so the FAILED state is kept. Resume works across requests.
4. **References are by natural code inside the job company only.** UUID columns are never accepted, and an unknown
   code gives the same answer whether it exists in another company or not (no existence oracle).
5. **BOMs**: an import never activates. A changed ACTIVE or OBSOLETE BOM gets a new DRAFT version; activation stays
   a user action.
6. **Internal requisitions** are keyed by a file `reference`, stored as `source={type:"dataio.import", number:ref}`.
   On export the reference is the stored reference or the document number. The number itself always comes from the
   sequence.
7. **The exógena pack is immutable** (the owner has no update). A changed pack requires a new `version`; a pack of
   another company with the same key is refused, never reused.
8. **Treasury concept** extra fields (`requires_party`) can only be set on create, because the owner update refuses
   them. A change to them is a row error.
9. **Branches**: `default_warehouse_id` is not part of the template, because warehouses need a branch first. Set it in
   the UI after both exist.
