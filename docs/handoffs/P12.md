## Online-finalization boundary (text for `docs/modules/pos.md`, CCR P12-1)
A POS sale is final only when the server commits `POST /api/v1/pos/tickets:checkout`: that single transaction assigns the
DEE POS number, computes taxes, issues stock, posts the GL and the drawer/AR effect and writes the outbox event for the DEE
transmission. When the terminal cannot reach the server the PWA shows "Sin conexión: no se pueden finalizar ventas"; the
cashier may browse the cached catalog and build or park carts as local, unposted drafts ("BORRADOR – sin valor fiscal": no
number, no CUDE, no stock, no GL). Checkout, tender capture, returns, cash movements, session close and receipt printing are
disabled and nothing is queued. On reconnect the draft is resubmitted through the normal checkout; the server recomputes
prices/taxes/stock, shows any difference and commits only after the cashier confirms. A DIAN/PT outage while our server is up
is not an offline case: the checkout commits in-line and P15's contingency flow handles the DEE. The `[A]` capability
`pos_offline_fiscal_selling` (disconnected fiscal selling with per-terminal number blocks, local CUDE, GL/stock at sync) is
**not built** in this edition: the flag stays off, `kernel.sequences.allocate_terminal_block` fails closed, the checkout refuses
`offline` requests, and the production startup refuses the flag without the EG-13 evidence.

## How to use it
```text
POST /api/v1/pos/configs        {name, branch_id (same company, required), warehouse_id (of that branch), location_id?, price_list_id?, numbering_range_id? (fiscal POS range), allowed_tenders?, cash_limit?, blind_count?}
POST /api/v1/pos/terminals      {code, name, config_id}      → POST /terminals/{id}:register {parameters{device_key}}
POST /api/v1/pos/sessions:open  {parameters{terminal_id, opening_cash}}
POST /api/v1/pos/tickets:preview  {parameters{session_id, lines[{barcode}|{item_id, presentation_id?, quantity}]}}
POST /api/v1/pos/tickets:checkout (Idempotency-Key = client_uuid) {parameters{client_uuid, session_id, lines, payments[{type, amount|tendered, reference?}], expected_total?}}
POST /api/v1/pos/returns        {original:{type:"pos.ticket", id}, lines?[{line_no, quantity}], refund_tender}  → :post (supervisor)
POST /api/v1/pos/cash-movements {session_id, movement_type IN|OUT, amount, reason}
POST /api/v1/pos/sessions/{id}:close {parameters{counted{CASH, CARD…} | denominations{face: count}, deposit_amount?}}
GET  /api/v1/pos/reports/z?session_id= · GET /api/v1/pos/catalog-snapshot?config_id= · GET /api/v1/kpis/pos?period=YYYY-MM
```
Company setup: account roles `CASH_POS`, `CASH_DIFFERENCE`, `CASH_TRANSFER`, `BANK_TRANSIT`, `CARD_CLEARING`,
`VOUCHER_LIABILITY`, plus the sales roles `REVENUE`, `VAT_PAYABLE`, `COGS`, `INVENTORY`; a fiscal `kernel.sequences` row
`POS` (the DIAN numbering resolution is EXTERNAL tenant data; tests use the synthetic `SETP` range, NOT a real resolution).

## Decisions taken under ambiguity
1. **Reuse of P10a**: pricing (`sales.pricing.engine`, D-024), parsing/policy/audit helpers and the generic secured resource
   views come from `sales`; POS adds only its own rules. Kits are exploded through P10a's `KitExplosion` port.
2. **POS price list**: applied through a transient party carrying `price_list_id` (engine list level); a named customer's own
   pricing wins.
3. **Discounts**: the per-user D-024 limit applies (default 0 %); a discount beyond it is refused at the counter
   (`pricing_override_requires_approval`) — no supervisor-override flow in this edition.
4. **Fiscal number**: the `POS` fiscal sequence (`numbering_range_id` pins one range); no range → `numbering_range_missing`.
5. **Tender roles**: CASH→`CASH_POS`, CARD→`CARD_CLEARING`, TRANSFER/QR→`BANK_TRANSIT`, VOUCHER→`VOUCHER_LIABILITY`; journal `SALES`.
6. **Contract field classes followed literally**: `payments`, `opening_cash`, `counted_cash`, `difference`, cash-movement
   `amount` are confidential, so the `cajero_pos` role (max internal) does not receive them; the receipt shows totals and change.
7. **"Other sessions" row rule** = holders of `pos.z_report.read` (no supervisor role exists; CCR P12-1 asks for one).
8. **Returns** are internal documents (`DVP-` numbers); the DEE credit note is P15's (CCR P12-1). Partial returns prorate
   amount/tax/cost; the last returnable units take the remainder.
9. **To-invoice** stores the buyer request in `pos_invoice_request` (the posted ticket stays immutable); B-06 (annex rule
   on annulling an issued DEE) is flagged for P15.
10. **Hardware [A]** (ESC/POS bridge, customer display, scale) not built: browser print of the committed receipt only;
    scanners work as keyboard input.
11. **Pages** (`frontend`): offline = browser offline OR a network error on a server call (the hook only knows the browser).

  this task (P08 owns the PWA shell).
* Z report is JSON (ReportResult); its PDF goes through P17's DocumentRenderer later.
* KPI `pos.kpi.read` is not granted by any role template yet (CCR P12-1); `pos.supervise` resolves through P04's alias.
