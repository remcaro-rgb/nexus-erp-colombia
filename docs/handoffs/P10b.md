## What was built

**Bootstrap** (`sales/portal/extension.py`, `urls.py`; CCR P10b-1). Same accepted pattern as P11b: importing
`sales.portal` (which `sales.urls` does whenever the URL configuration loads; the part tests at collection) adds
`sales/portal/migrations` to the `sales.migrations` search path (a `sys.meta_path` finder survives Django's reload),
imports the part models (app label `sales`), and `sales.portal.urls` registers the absolute mount
`api/portal/v1/customer/` in `SalesConfig.EXTRA_URL_MOUNTS` before `erp.discovery` reads it.
Migrations `0101_p10b_portal` (2 tables) and `0102_p10b_rls_guards` (FORCE RLS tenant + company on both).

**Data model** (`models.py`): `CustomerRequest` (QUOTE items+qty / PROFILE_CHANGE allow-listed party fields / GENERAL
message; `SUBMITTED → QUOTED → ORDERED`, `APPROVED`, `REJECTED`, `RESOLVED`; number `SOLC-`), `PaymentIntent`
(documents = own invoice ids, amount, simulated provider + ref, `CREATED → SUCCEEDED_SIMULATED | FAILED`,
`receipt_id` of the DRAFT RC; `CONFIRMED_BY_TREASURY` is derived on read once treasury posted that RC).

**Portal API** (`views.py`, `/api/portal/v1/customer/*`, base `iam.external.portal.PortalView`, `portal_kind = customer`):

| Route | Behaviour |
|---|---|
| `quotes`, `orders`, `invoices`, `credit-notes`, `receipts` (+`/{id}`) | P10a frozen projections (`sales.interfaces.portal_*`, contract `Customer*` fields only). Drafts are internal (404). |
| `quotes/{id}:accept` | SENT + not expired → quote ACCEPTED → **DRAFT** sales order (`order_from_quote`, channel `portal`) → quote ORDERED; linked request ORDERED. Nothing confirmed, reserved or posted. |
| `invoices/{id}/pdf|xml`, `credit-notes/{id}/pdf|xml` | Synthetic documents labelled **`SINTÉTICO — sin validez fiscal`** (`documents.py`); audited downloads; `Cache-Control: no-store`. |
| `open-items` | Own open invoices (number, due date, balance) to choose what to pay. |
| `statement?from=&to=&format=json|csv|pdf` | ReportResult from P10a `ar.statement` + `ar.aging` of the party's open items; CSV/PDF labelled. |
| `payment-intents` (GET/POST, `/{id}`), `payment-intents/{id}:simulate` | D-021: amount > 0, minor units, same currency, ≤ open balance of the chosen own invoices (`payment_intent_amount_invalid`); success → DRAFT recibo de caja (`sales.Receipt`, applications oldest-due first) **without posting**; failure → FAILED; re-simulation 409. |
| `requests` (GET/POST, `/{id}`), `profile`, `kpis?period=` | Requests as above; profile = the linked party (legal name, NIT-DV, e-mail); KPIs `cp_saldo_pendiente`, `cp_facturas_vencidas`, `cp_pedidos_en_curso`, `cp_pagos_periodo` (+ previous period) in the shell's `KpiValue` shape. |

Security: party/company always from the token's external account; every repository query filters
`tenant + company + party` **and** goes through `PolicyEngine.scope_queryset` (portal scope); a foreign id is a 404
(`portal_document_not_owned` / `not_found`, no existence oracle); scope ids in query/body → 403
`external_account_scope_violation`; field allow-lists per view; internal tokens refused (401) and portal tokens refused
by `/api/v1/*`; writes need `Idempotency-Key` (replay returns the stored response); every write and download audited;
throttles of the secured base (per principal + tenant).

**Back office** (`/api/v1/sales/…`): `portal-requests` (list/detail, filters), `:quote` (DRAFT quote through P10a
`create_quote` with D-024 prices, optional `send`), `:approve` (PROFILE_CHANGE applied with P10a `update_party`; GENERAL
closed), `:reject` (reason required); `payment-intents` (treasury view with `receipt_id`). Each needs its own `sales.*`
permission (deny by default) plus the P10a permissions of the step it triggers.

**Frontend** (`frontend/src/features/sales/portal/`): `portal.descriptor.ts` (auto-discovered by the P08 portal shell,
pages for the 7 non-dashboard menus of `portals › clientes`), `Pages.tsx` (Cotizaciones with Aceptar, Pedidos, Facturas y
notas with PDF/XML links, Pagos y recibos with the simulated payment form, Estado de cuenta with PDF/CSV, Solicitudes,
Perfil), typed `api.ts`, pure `model.ts` (exact BigInt decimal sums, payment/request validation, es-CO messages).

## How to use it
```text
# customer (erp-portal token of an ACTIVE customer external account)
POST /api/portal/v1/customer/requests   {request_type: QUOTE, message, items[{item_id, quantity}]}
POST /api/portal/v1/customer/quotes/{id}:accept
POST /api/portal/v1/customer/payment-intents {documents:[invoice_id…], amount:{amount, currency}}
POST /api/portal/v1/customer/payment-intents/{id}:simulate {parameters:{outcome: success|failure}}
GET  /api/portal/v1/customer/statement?from=2026-01-01&to=2026-11-30&format=pdf
# back office (erp-web token)
POST /api/v1/sales/portal-requests/{id}:quote {parameters:{send:true, valid_until}}
GET  /api/v1/sales/payment-intents   → receipt_id → POST /api/v1/sales/receipts/{receipt_id}:post (treasury)
```
Onboarding of the customer account is P04's invitation flow (`/api/v1/iam/external-accounts`, kind `customer`,
`party.id` = the sales party id).

## Decisions taken under ambiguity
1. **Contract enums win** over the addendum names: `intent_status` uses `SUCCEEDED_SIMULATED`/`FAILED`/
   `CONFIRMED_BY_TREASURY` (contract) for the addendum's `SIMULATED_SUCCEEDED`/`SIMULATED_FAILED`; `EXPIRED` not implemented.
2. **RC draft = P10a `sales.Receipt` DRAFT**, created automatically on the simulated success (system action under D-021,
   audited with the external principal), posted manually by treasury with its own permission. Treasury (P12/P16) has no
   voucher model yet (CCR P10b-3).
3. **Quote acceptance creates a DRAFT order** (not confirmed): credit check and stock reservation remain internal
   decisions (`orders/{id}:confirm`). The acceptance itself is done by the portal service (the customer has no
   `sales.quote.update`), guarded by `portal.customer_quote.update` (new code; `accept` is not a catalog action).
4. **One request model** for quote requests, profile changes and general requests (`request_type`), instead of separate
   `PortalQuoteRequest` / `CustomerProfileChange` tables — the contract has a single `/requests` resource.
5. **Simulated provider is a route** (`:simulate`, DEV fixture) rather than an automatic success, so tests and the UI can
   exercise both outcomes; the UI completes the simulation right after creating the intent.
6. **Fiscal artefacts are always labelled** (this edition is DEV-only; there are no real DIAN documents). The XML is a
   UBL-shaped synthetic layout marked NOT LEGALLY VERIFIED (the DIAN Anexo Técnico is EXTERNAL input).
7. Quote totals shown are P10a's (before tax: P10a computes taxes at invoicing).
8. `portal.customer.read` (registry permission of the portal and its KPIs) is not a catalog code; the KPI route uses
   `portal.customer_profile.read` (same pattern as P11b/P13a).

## Known limitations
* Downloads are plain `<a download>` links (as in the employee portal); a bearer-token session needs an authenticated
  download helper in the P08 shell (CCR P10b-3).
* Quote requests take item ids (no item catalogue/picker for external users yet). No ticket module (`[A]`).
* Statement in COP only (as P10a). Payment intents do not expire.
