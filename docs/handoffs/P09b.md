## What was built
* **Pure encoders** (`barcodes/core.py`): Code 128 (automatic A/B/C subset switching, mod-103 check, module strings,
  decoder for tests), GS1 mod-10, GTIN-8/12/13/14 validation and GTIN-14 normalisation, EAN-13 modules (L/G/R tables,
  R and G derived from L), EAN-13 from a user-entered prefix, restricted-circulation detection (prefixes 20–29).
* **Barcodes** (`barcodes/service.py`, models `Barcode`, `Gs1Prefix`): internal Code 128 `<COMPANY>-<8 digits>` from the
  gap-free `kernel.sequences` code `BARCODE` (D-004), unique per company in the DB; EAN-13 only from a prefix a user entered
  (`gs1_prefix_missing` otherwise), stored and reused; restricted prefixes are labelled "uso interno, no licencia GS1"
  and never claim ownership (DB check constraint). Imported GTINs are validated, never claimed; duplicates are checked across
  all spellings (UPC-A / EAN-13 / GTIN-14) and across item GTIN, presentation and location barcodes. Lookup resolves item,
  presentation (with factor), location and lot through each owner's `scope_queryset`, so anything outside the caller's
  company/warehouse scope is `barcode_unknown` (404), never 403 (no existence leak). Event `inventory.barcode.generated.v1`.
* **Labels** (`barcodes/labels.py`): templates with a fixed field list (`value, code, name, presentation, lot, expiry_date,
  location, company`) — no cost field can exist; print jobs render label data (hash), PDF via `DocumentRenderer`
  template `inventory.label` (pdf hash, status DOWNLOADED), deterministic pure-Python PNG preview.
* **Issues** (`issues/service.py`, models `IssueConcept`, `StockIssue`, `StockIssueLine`, migration 0101 with company/branch/
  warehouse FKs, immutability triggers and forced RLS on all 7 tables): seeded concepts CONSUMO (cost center), CONSUMO_DIRECTO
  (cost center + ítem contable), BAJA (coded reason VENCIDO/DANADO/OBSOLETO/PERDIDA/OTRO), MUESTRA, OTRO (reason). Each maps to
  an account-determination role, never a hard-coded account. Flow DRAFT → SUBMITTED (stock reserved, approval requested) →
  APPROVED/REJECTED → POSTED → REVERSED; CANCELLED releases reservations. Post = stock issue at average/FIFO cost + balanced
  Decimal journal (Dr concept role with dimensions, Cr INVENTORY, warehouse branch) + event, one transaction. Simulate runs
  the same path in a rolled-back savepoint. Reverse needs a reason and returns stock at original cost/bin/lot plus a GL reversal.
* **API**: `barcodes:generate` (202 Operation), `barcodes:validate`, `barcodes/lookup`, label-templates, label-print-jobs
  (+`/pdf`, `/preview.png`), issue-concepts, issues (+`:submit/:approve/:post/:reverse/:simulate`, `issues:export` CSV,
  `/pdf`). Cost fields (`total`, line costs, thresholds) are `confidential`; the CSV omits `valor_cop` for roles without them.
* **Frontend**: `IssuesPage` (create with scan input, dimension/reason pre-validation, simulate journal preview, actions per
  state), `IssueConceptsPage`, `BarcodesPage` (scan, generate, import/validate, print with SVG preview), `ScanInput`,
  `LabelPreview`; vitest for both model files.

## Decisions (non-obvious)
* State names follow the contract (`SUBMITTED`, not `PENDING_APPROVAL`). Reverse is gated by `inventory.issue.void`.
* Approval threshold is checked against the estimated value at the current average cost; the posted value is the actual cost.
* The separate scraps endpoint is covered by the BAJA concept (same document, coded reason); no second document type.
* QR / GS1-128 symbologies are not encoded yet; templates asking for them fall back to Code 128 (recorded on the job).
* No `inventory.issue.posted.v1` value line is emitted for zero-value lines; the event still fires per document.
* The UI `ApiClient` has only get/post/patch, so the pages cannot cancel (DELETE) or download the PDF yet; the API supports both.
* Pages and the `Labels` service need wiring in P09a-owned files → CCR P09b-1. Seeds and migration merge → CCR P09b-2.
