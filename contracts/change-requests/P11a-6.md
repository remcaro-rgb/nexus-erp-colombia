# CCR P11a-6 — approval policies, scheduler job and registry permission codes (P07 / P21 / P04 / P08)

* From: P11a · To: P07, P21, P04, P08 · Type: configuration · Status: OPEN

1. **Approval policies** (P21 seed; P07 `DbWorkflowService.request_approval` raises `not_found` without a policy):
   `purchasing.rfq.award` (document type `purchasing.rfq_award`; approver role with `purchasing.rfq.approve`) and
   `purchasing.vendor_invoice.mismatch` (document type `purchasing.vendor_invoice`; three-way match breach / invoice
   without PO). P11a additionally enforces SoD itself (approver ≠ RFQ buyer ≠ award proposer; PO approver ≠ creator/
   submitter).
2. **Scheduler job** (P07): register `purchasing.rfq.close_due` → `purchasing.services.rfq.close_due_rfqs(uow, company)`
   every 15 minutes per company (closes SENT RFQs whose deadline passed, D-010).
3. **Registry permission codes** (P04/P08 nav filter): `module-registry.json` › compras uses two-part codes
   `purchasing.read`, `purchasing.write`, `purchasing.receive`, `purchasing.kpi.read`, `payables.read`, `party.read`.
   Please map them to catalog codes (e.g. `purchasing.read` ⇐ any `purchasing.*.read`, `purchasing.receive` ⇐
   `purchasing.receipt.read`, `purchasing.write` ⇐ `purchasing.order.create`, `payables.read` ⇐
   `purchasing.vendor_invoice.read`, `party.read` ⇐ `purchasing.supplier.read` / `sales.party.read`).
4. **Supplier master**: P11a keeps a purchasing supplier profile (`purchasing_supplier`: rating, payment terms,
   currency, `party_id` → P10 party). P10a's `PartyService` should expose vendor parties; the profile then references
   them by `party_id`.
