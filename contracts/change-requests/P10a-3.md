# CCR P10a-3 — consumers of the sales events (e-invoicing, treasury, reporting)

* From: P10a · To: P15 (e-invoicing), P12 (treasury), P17 (reporting) · Type: integration note · Status: OPEN
* `sales.invoice.posted.v1` (payload `{invoice_id, number, party, total, journal_entry_id}`) is the hand-off of a posted
  sales invoice to electronic invoicing: P15 consumes it (inbox dedupe), builds the DIAN document and registers it with
  `kernel.interfaces.fiscal.FiscalDocuments`; the sales API reads the fiscal status live through that interface
  (`fiscal_status` shows `QUEUED` until P15 registers the document). Credit / debit notes: `sales.credit_note.posted.v1`
  (debit notes post the same entry shape; P15 can read them through `sales.models.SalesNote` with `kind=DEBIT`).
* Fiscal numbering: invoices/notes take their number from an active `kernel_sequence` row with `is_fiscal=True` and code
  `FV` / `NC` / `ND` valid on the document date (the DIAN range is EXTERNAL data entered by the tenant; none →
  `numbering_range_missing`). P15 owns creating those rows from the numbering resolutions.
* Treasury: `sales.receipt.posted.v1` after a customer receipt is applied; `sales.services.ar.SalesArOpenItems`
  implements `kernel.interfaces.ArOpenItems` (open_items/apply/unapply) and is registered by `SalesConfig.ready()`.
