# CCR P07-3 — contract additions observed while implementing P07 (P02 / integrator)

* From: P07 · To: P02 (contracts) / integrator · Type: additive · Status: OPEN
1. **Error codes** used by workflow and missing from `contracts/errors.yaml` (module workflow):
   `approval_not_pending` 409, `approver_not_assigned` 403, `approval_already_decided` 409, `approver_unresolved` 422,
   `delegation_required` 403, `human_approval_required` 403, `formula_hash_mismatch` 409, `retention_locked` 409,
   `signed_url_invalid` 403, `signed_url_expired` 403, `attachment_infected` 422, `dsr_identity_unverified` 409.
   (`sod_violation`, `approval_required`, `production_endpoint_refused`, `filter_invalid` already exist.)
2. **Events** emitted and not in `contracts/events/catalog.yaml`: `workflow.notification.email_requested.v1`
   (payload `{notification_id: uuid}`, consumed by the notifications worker → local mail capture) and
   `workflow.webhook.ping.v1` (`:test` deliveries only, never through the outbox).
3. **Formula status naming.** FEATURES-ADDENDUM uses `DRAFT → PENDING_APPROVAL → ACTIVE → RETIRED`; the frozen
   `Formula.formula_status` enum is `DRAFT | SUBMITTED | APPROVED | RETIRED`. The API maps PENDING_APPROVAL→SUBMITTED
   and ACTIVE→APPROVED; `Formula.status` (record) is ACTIVE, or ARCHIVED once retired. No contract change needed if
   the integrator accepts this mapping.
4. **`:validate` / `:simulate` bodies.** Both use the generic `ActionRequest`: the formula draft goes in
   `parameters` (same fields as `FormulaInput` plus `domain`, `depends_on`), simulate inputs in
   `parameters.values`; results come back in `ActionResult.data` (validation report / explain snapshot).
5. **`tests` field.** `FormulaInput.tests` is an object; the API stores `{"cases": [{inputs, expected,
   expected_error?, name?}]}` (a bare list is accepted too).
