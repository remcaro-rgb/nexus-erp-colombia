# CCR P17a-1 — WeasyPrint (D-005) vs the pure-Python PDF engine shipped by P17a

* From: P17a · To: integrator / owner of `pyproject.toml` + `uv.lock` (P01/P03), DEV task · Type: dependency decision · Status: OPEN
* D-005 names WeasyPrint (exact pin in `uv.lock`). It is not in `pyproject.toml`, adding it is outside P17a's owned paths,
  and WeasyPrint also needs system libraries (Pango/HarfBuzz) that the app image and the CI runners do not install.
* P17a therefore implements `kernel.interfaces.DocumentRenderer` with a **deterministic pure-Python PDF 1.4 engine**
  (`backend/documents/pdf/`: standard-14 fonts with WinAnsi encoding, grayscale image XObjects for barcodes, no
  timestamps, `/ID` = SHA-256 of the page content) driven by a sandboxed template language (`documents/markup.py`).
  It satisfies the D-005 contract (pure, deterministic bytes, visible watermark) and the G3 tests (real PDFs parsed
  back, barcode raster decoded). The contract field `engine` keeps the value `weasyprint` (the only enum value).
* Request: decide whether WeasyPrint is still wanted. If yes: add `weasyprint==<pin>` + system packages to the image,
  and P17 adds an `engine` implementation behind the same `DocumentRenderer` (templates are engine-neutral markup;
  the HTML preview already exists: `layout.to_html`). If no: amend D-005's wording to "WeasyPrint or the pure-Python
  engine" and the `engine` enum.
