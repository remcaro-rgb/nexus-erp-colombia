# CCR P22b-5 / DEF-P22-009 — SecuredView leaks the request's tenant scope on unhandled errors (P04)

* From: P22b · To: P04 (`backend/iam/api/base.py`) · Status: OPEN · Severity: high (ADR-003, invariant 12)
* Defect: DEF-P22-009 (strict xfail `tests/cross_module/scenarios/test_xm_fin01_stk01_atomicity.py::test_p22b_secured_view_releases_transaction_and_context_on_unhandled_error`).
* Observed: `SecuredView.initial()` enters `tenancy.activate(ctx)` (and `ModuleSecuredView` also `tenancy.scope(ctx)` =
  `transaction.atomic()` + `SET LOCAL` tenant binding) into `self._ctx_stack`; the stack is closed only in
  `finalize_response()`. DRF does not call `finalize_response()` when an exception that the exception handler does not turn into
  a response escapes the handler (`raise_uncaught_exception`). Reproduced on `GET /api/v1/ledger/periods` with a failure before
  the 2nd SQL statement: the thread's connection stays `in_atomic_block` with the tenant binding, and the activated context
  stays in the contextvar. Worse, the suspended `tenancy.scope` generator is finalised later by the garbage collector **on the
  collecting thread**, whose `Atomic.__exit__` then pops a savepoint of *that* thread's transaction (seen in the P22 suite: it
  corrupted an unrelated test's transaction).
* Request: close `_ctx_stack` in a `try/finally` around `dispatch()` (or override `handle_exception` to close it before
  re-raising), so the scope is released on every exit path.
