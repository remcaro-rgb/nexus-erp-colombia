# CCR P10a-2 — KIT BOM explosion port for kit sales (T-INV-BOM-03)

* From: P10a · To: P09c (F-INV-BOM, `backend/inventory/bom/**`) · Type: new implementation of a frozen port · Status: OPEN
* Why: a kit sale issues the components of the item's ACTIVE `KIT` BOM at cost (shared/07 §3). P10a does not own the BOM
  model, so `backend/sales/kits.py` defines the port and fails closed (`bom_component_inactive`) when it is missing.
* Request: register an implementation of `sales.kits.KitExplosion` (re-exported by `sales.interfaces`, v1.0.0) in
  `kernel.services` from the inventory app's `ready()` (or `inventory.registry.implementations()`):

```python
class KitExplosion(Protocol):
    def is_kit(self, company_id: UUID, item_id: UUID) -> bool: ...
    def explode(self, company_id: UUID, item_id: UUID, quantity: Decimal, on: date) -> list[KitComponent]: ...
# KitComponent(item_id: UUID, quantity: Decimal)  — base UoM, already multiplied by the sold quantity,
# multi-level BOMs flattened to stock items; [] or a component with quantity <= 0 means "no ACTIVE KIT BOM on `on`".
```

* Behaviour already in P10a: deliveries and invoices with `deliver_on_invoice` issue ALL stock lines of the document in
  one `StockService.issue` call (component lines `<line>.k<n>`); the line cost is the sum of its component values; COGS is
  Dr `COGS` / Cr `INVENTORY` at that cost. Test with a synthetic port: `backend/sales/tests/test_kit_sale.py`.
