# CCR P10b-3 — consumers of the customer portal (treasury RC, fiscal artefacts, PDF renderer, portal shell KPIs)

* From: P10b · To: P12/P16 (treasury), P15 (e-invoicing), P17 (DocumentRenderer), P08 (portal shell), P22d (E2E) · Type: integration note · Status: OPEN
* Treasury (D-021): a simulated payment success writes a **DRAFT** `sales.Receipt` (number `RCA-…`, applications to the
  intent's invoices, oldest due first, `bank_role = BANK`); nothing posts. Treasury lists the intents at
  `GET /api/v1/sales/payment-intents` (`receipt_id`) and posts the RC with the existing P10a `POST /receipts/{id}:post`;
  the intent then reads `CONFIRMED_BY_TREASURY`. When P16's voucher model (RC, `PaymentStatus`) replaces the sales receipt,
  `sales.portal.service._draft_receipt` is the single place to switch.
* P15: the invoice XML is a UBL-2.1-*shaped* synthetic document (NOT LEGALLY VERIFIED); the CUFE is read from
  `kernel.interfaces.FiscalDocuments.status` when registered (else `SIN-CUFE (SINTÉTICO)`). P15 may later serve the real
  XML it generated; the label must stay in DEV.
* P17: PDFs go through `kernel.interfaces.DocumentRenderer` when registered (`watermark = "SINTÉTICO — sin validez fiscal"`,
  templates `sales.portal.sales.invoice`, `sales.portal.sales.credit_note`, `sales.portal.statement`); if the rendered bytes
  do not contain the label the built-in minimal PDF is served instead.
* P08: the dashboard KPIs are served at `/api/portal/v1/customer/kpis` (shell calls `/api/portal/v1/kpis?portal=customer`).
  File downloads are plain links (`<a download>`) like the employee portal; with bearer-token sessions the shell needs an
  authenticated download helper (fetch → blob) for all portals.
